## 0. Project Context

**Planificador de cuatrimestre**: a web app where a UNED student registers the courses of the current semester (term) and sees every task, project, exam and forum with its due date in one place. Goal: open the app and know in 5 seconds what is due this week.

- **Stack**: React + Vite + TypeScript, Tailwind CSS, Zustand (persisted to `localStorage`), date-fns, Vitest + Testing Library, Playwright.
- **No backend**: there is no server, API or database. All data lives in the browser under a single versioned `localStorage` key (`planner:v1`). See [data-model.md](./data-model.md).
- **Deployment**: Vercel, connected to GitHub. Every push to `main` is published.

## 1. Core Principles

- **Small tasks, one at a time**: Always work in baby steps, one at a time. Never go forward more than one step.
- **Test-Driven Development**: Start with failing tests for any new functionality (TDD), according to the task details.
- **Type Safety**: All code must be fully typed. No `any` unless justified in a comment.
- **Clear Naming**: Use clear, descriptive names for all variables and functions.
- **Incremental Changes**: Prefer incremental, focused changes over large, complex modifications.
- **Question Assumptions**: Always question assumptions and inferences.
- **Pattern Detection**: Detect and highlight repeated code patterns.

## 2. Language Standards

- **UI text in Spanish**: Everything the user sees (labels, buttons, headings, validation and error messages, empty states, date formatting via the date-fns `es` locale) is written in Spanish.
- **Everything else in English**:
    - Code (variables, functions, types, components, comments)
    - Documentation (README, guides, docs/)
    - OpenSpec artifacts (proposals, specs, designs, tasks)
    - Configuration files and scripts
    - Git commit messages
    - Test names and descriptions (assertions may contain the Spanish UI strings they check)

## 3. Testing and Quality Gates

- **Minimum coverage: 70%** (lines, branches, functions, statements). Enforced by `npm run test:coverage` through the thresholds in `vite.config.ts`.
- **Unit and component tests**: Vitest + Testing Library, colocated as `*.test.ts(x)` next to the code they test.
- **E2E tests**: Playwright, in `e2e/`. One flow per main user story.
- Before a task is marked done: `npm run lint`, `npm run build` and `npm run test:coverage` pass. E2E (`npm run test:e2e`) also passes for user-facing changes.

## 5. Project Skills

- Skills live in `ai-specs/skills`.
- When a request matches a skill, load and follow the corresponding `SKILL.md` automatically before continuing.
- Also load any referenced files in the skill folder (for example, `references/*.md`) when the skill requires them.

## 6. Canonical Sources and Multi-Agent Portability

- **Canonical Source**: Reusable agents and skills live in `ai-specs/`. The copies in `.claude/agents`, `.claude/skills` and `.agents/skills` are generated mirrors. Never edit the mirrors directly.
- **Copies instead of symlinks**: This project is developed on Windows, where symlinks need Developer Mode. Mirrors are copies created by `npm run sync:ai-specs` (`scripts/sync-ai-specs.mjs`).
- **Update Safety**: Whenever a file in `ai-specs/` is added, renamed, moved or removed, run `npm run sync:ai-specs` before considering the change complete.
- **OpenSpec-owned files**: `openspec-*` skills and `.claude/commands/opsx/` are generated by `openspec init` / `openspec update`. They are not part of `ai-specs/` and the sync script does not touch them.
- **Completion Gate**: A change is incomplete if it leaves stale mirrors.

## 7. Mandatory OpenSpec Artifact Updates for Post-Apply Changes

When a new fix/change request appears after `opsx:apply` (or `/apply`) and before `opsx:archive` (or `/archive`), agents must treat it as a spec update first, not as an informal "fix this quickly". It's the core principle of openspec, documentation is the source of truth.

Required order:

1. Update the current OpenSpec change artifacts that are affected (for example: scenarios, requirements/specs, and `tasks.md`). Don't add tasks as "bugfixes" but as part of the initial design, thus in the proper section
2. If artifact regeneration is needed, run the corresponding OpenSpec step (`opsx:continue`, `opsx:ff`, or equivalent) before coding.
3. Implement code only after artifacts reflect the new request.
4. Re-run verification against the updated artifacts before archiving.

Do not apply direct code-only fixes in this window without updating OpenSpec artifacts.
